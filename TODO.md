## Code review — 2026-10-12

Completed feature designs are in [Shielding Taunt](docs/shielding-taunt.md), [Set Hero Points](docs/set-hero-points.md), [Ask a Question About](docs/ask-a-question-about.md), and [Zone Builder](docs/zone-builder.md). The former Recall Knowledge feature/design notes have moved out of this backlog.

Review scope: feature entry points, privileged transport/worker paths, saved operation markers, Hero Point scheduling, and selected runtime transactions/lifecycle paths. The five reproductions below used the actual module functions with isolated document/network-free mocks; they establish code-path behavior, not a live Forge reproduction. Application code was not changed during this review.

### Bugs and correctness gaps

- [x] **[P1] Stop queued zone transactions after an active-GM handoff.** `scripts/runtime.js`: authoritative event/recovery entry points, `withState`, and `writePayload`.

  **Evidence:** Hold a Region state lock, enqueue a `tokenTurnEnd` event while this GM is authoritative, switch `game.users.activeGM`, then release the lock. The old GM still executes the queued trigger and commits its payload. The entry check happens before waiting; the transaction/commit does not revalidate authority. This can duplicate effects or overwrite the new GM's state.

  **Resolution (2026-10-13):** Capture an authority lease when automatic work is accepted and retain it across Region/shared-immunity locks, nested recovery calls, fresh payload reads, and timers. Recheck before queued callbacks, Item changes, chat cards, Region/world-state writes, and deferred actions. Observed authority changes invalidate the generation, cancel old timers, and clear transient occupancy/alert caches; a runtime upgrade also retires earlier leases. New authority recovery can start without joining a stale recovery pass. Direct GM dismissal remains deliberately unscoped so a secondary GM can still manage zones. Already-dispatched Foundry document updates cannot be recalled; their remaining follow-up work is suppressed.

  **Validation:** All 323 automated tests and full ESLint pass. Sixteen new regressions cover queued Region events, authority leaving and returning, mid-await effect/damage/cleanup work, commit/deferred-action boundaries, save-card recovery, shared-state queues and mutators, save-resolution locks, source-driven dismissal, secondary-GM dismissal, activation timer recovery, runtime retirement, and overlapping recovery generations. Live two-GM Forge verification remains in the checklist below.

- [x] **[P2] Serialize independent Hero Point changes and detect stale retry plans.** `scripts/hero-points.js`: `setHeroPoints` and the dialog request path; `scripts/hero-points-worker.js`: authoritative per-Actor queues and retained operations.

  **Review evidence (2026-10-12):** Two concurrent `setHeroPoints(1, actor)` calls from zero both planned a total of one and left one point instead of two. The dialog's busy flag protected one dialog, but the public API and other GM tabs did not share that guard. A retained partial-failure plan also had no conflict check against later external edits.

  **Resolution (2026-10-13):** Routed all point changes through the authenticated active-GM worker. Per-Actor queues calculate totals from the latest resource, join duplicate operation IDs, and preserve completed entries on retry. Pending retries check the original value, maximum, and preceding module receipt before writing; stale plans require a fresh review. Resource updates atomically include a receipt to identify committed writes after a lost acknowledgment. Missing or expired retry plans fail closed. Preserved the dropdown, recipient resolution, additive API default, bounded totals, and GM-only summaries; documented the retry options and ten-minute plan lifetime in `docs/set-hero-points.md`.

  **Validation:** All 299 automated tests and full ESLint pass. Added coverage for concurrent awards/spends, unrelated Actor queues, duplicate IDs, completed entries changed before retry, stale values/maxima/receipts, cancelled and uncertain writes, lost/expired plans, queued authority changes, authenticated two-GM routing, and player rejection. Live Forge checks remain in the validation checklist below.

- [x] **[P2] Reserve reminder creation before awaiting the User update.** `scripts/hero-point-reminders.js`: `createHeroPointReminder`; `scripts/hero-point-reminder-worker.js`: authoritative creation reservations and User queues.

  **Evidence:** Two concurrent calls for the same GM and `HH:mm` value both miss the existing-record check and persist distinct IDs for the same `remindAt`. Fixed ChatMessage IDs prevent duplicate delivery of one record, but not delivery of these two different records. The current dialog guard does not protect direct API calls or another tab.

  **Resolution (2026-10-13):** Send the creating GM's absolute timestamp through authenticated active-GM transport. Reserve matching recipient/time requests synchronously and serialize creation per recipient; recheck saved flags and GM permissions after waiting and before writing. Reuse legacy reminder IDs. New reminders derive a stable sixteen-character ID from recipient and timestamp so independent tabs, retries, and handoffs converge on the same flag key. Confirm a lost acknowledgment from the exact stored record; release failed reservations for retry. Preserved local-time interpretation, private recipients, clearing, and fixed-ID chat delivery.

  **Validation:** All 335 automated tests and full ESLint pass. Twelve new regressions cover simultaneous saves and one resulting delivery, independent worker instances, queued legacy-record discovery, committed and uncertain acknowledgments, late writes after delivery, reservation cleanup, queued handoff, malformed inputs and GM authorization, ID collisions, separate recipients, and authenticated secondary-GM routing. Live Forge tab/reconnect checks remain in the checklist below.

- [x] **[P2] Validate the provenance of persisted completion markers before reusing them.** `scripts/recall-knowledge-worker.js`: `completedQuestion`; `scripts/shielding-taunt-worker.js`: `completedOperation`; shared authorship validation in `scripts/utils.js`.

- [x] **[P2] Persist the full creation fingerprint for post-refresh zone retries.** `scripts/worker.js`: `oncePerCreationRequest` and `createZone`; `scripts/zone-creation.js`: `creationRequestFingerprint` and `initialRuntimeState`.

  **Evidence:** A fresh worker accepts changed configuration under an existing `creationOperationId` and returns the original Region as success. Only the local ten-minute cache compares the full request; the durable lookup checks operation ID and creator. A reload or cache expiry therefore changes replay validation semantics.

  **Resolution (2026-10-13):** Copy creation requests before waiting and use one versioned canonical JSON fingerprint for both the local cache and the initial Region's `state.creationFingerprint`. Capture requester, source token, Scene, full accepted raw configuration, preset ID/revision, activation choice, color, and placement. Sort object keys recursively while preserving array order; absent optional fields equal null. Search all Scenes for the creator's operation so changing Scenes cannot bypass replay validation. Compare the persisted fingerprint and owning Scene before returning an existing Region. Older Regions without a usable fingerprint remain playable/manageable, but their uncertain retries fail with instructions to review Manage Existing Zones; never infer/backfill an unverified request or create a duplicate.

  **Validation:** All 398 automated tests and full ESLint pass. Twenty-one new regressions cover every changed creation field in cached and fresh workers, cross-Scene reuse, canonical ordering, raw-config ID repair, input mutation during an await, cache expiry, missing/malformed legacy fingerprints, separate creators, executing-GM handoff, original rolled durations, and retries after live Region movement/configuration edits. Identical retries preserve the original Region without another creation, activation, duration roll, or announcement. Live Forge refresh/handoff checks remain below.

  **Review evidence (2026-10-12):** The pre-existing working-tree prompt edit omitted the plain-prose/no-Markdown instruction, causing the suite's contract assertion to fail. The response normalizer remained present, but the request no longer told the model to avoid formatting.

- [x] **[P2] Make preset saves retry-safe after an uncertain acknowledgment.** `scripts/builder.js`: `saveCurrentPreset`; `scripts/worker.js`: `oncePerPresetSaveRequest`, `completedPresetSave`, and `saveLibraryPreset`; `scripts/preset-save.js`: `presetSaveFingerprint`.

  **Inspection:** Library requests carry no durable operation ID. After a Save As commits but its socket reply times out, another click sends `recordId: null` and can create a second preset. A committed overwrite can instead return a stale-revision error when retried. Per-client serialization does not identify an already completed logical operation. This scenario was identified by inspection, not reproduced live.

  **Resolution (2026-10-13):** Freeze a requester-scoped operation ID and complete save request before sending it; retain both after transport failures or unconfirmed writes. Retrying the same Save/Save As confirms that request while preserving newer editor changes; ordinary worker rejections release the attempt. Join matching requests in the GM cache and atomically persist a full request fingerprint and original record snapshot alongside the preset in the Journal flag. Durable receipts return the original ID/revision after cache expiry, refresh, handoff, later edits, or deletion, without applying another overwrite or recreating a deleted preset. Stable Save As IDs prevent duplicate records across independent workers. Reject changed requests or incomplete receipts rather than infer completion. Keep existing library schema, authorization, revision checks, and post-commit index warnings; legacy callers without an operation ID retain their prior behavior. Retain receipts for the library's lifetime. Library queues remain local to each GM client; already-dispatched document writes cannot be recalled on handoff.

  **Validation:** All 421 automated tests and full ESLint pass. Twenty-three new regressions cover joined saves, committed/lost and unconfirmed acknowledgments, repeated overwrites, changed fingerprints, historical revisions/deletion, missing/incomplete receipts, queued request snapshots, independent workers, requester isolation, GM handoff, index failure, builder timeouts, transport failures, missing-GM retries, ordinary rejection, and preserving newer edits. Live Forge socket/reconnect checks remain below.
