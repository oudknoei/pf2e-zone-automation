## Direct OpenAI answers for Recall Knowledge

- [x] **Feature: Send the "Ask a question about ..." prompt directly to an LLM and show the answer privately to the GM.** Implemented with session-only key entry, a configurable Responses API endpoint, and private async answers. Automated validation covers the flow; live Forge/API verification is still pending. The design below records the intended behavior. Key entry belongs in Foundry's game settings UI, while the key itself exists only in the active GM's current browser session. The request runs from that browser, so Forge needs no server changes or separately hosted service.

### GM setup and session lifetime

Add **Configure Settings → PF2e Zone Automation → AI Connection**, using a GM-only settings submenu. This opens an ApplicationV2 dialog rather than registering the API key as a saved setting. Foundry supports custom settings menus with `restricted: true`; also check GM authorization in the dialog's handlers. [Foundry settings API](https://foundryvtt.com/api/v14/classes/foundry.helpers.ClientSettings.html)

The dialog contains:

- **API key:** a blank non-masked input. Never prefill it with the current key.
- Helper: **"Kept only until you reload or close this tab."**
- **Use for this session**, **Clear key**, and **Close** buttons.
- Status: **"Key entered for this session"** or **"No key entered"**. Entering a key does not imply that OpenAI has validated it.
- **Model:** a non-secret world setting, initially `gpt-6-luna`, editable by a GM. It supports Responses and configurable reasoning effort. Previously saved model choices remain until changed. [Model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna)
- **Reasoning effort:** a non-secret world setting with a dropdown for None, Low, Medium, High, Extra high, and Maximum; initially **Low**. Choose a value supported by the selected model. Omit the reasoning parameter for older non-reasoning GPT models.
- **Output allowance:** a non-secret world setting, initially **4,000 tokens**, covering reasoning and visible output combined. Accept whole numbers from 16 to 128,000; the selected model or endpoint may impose a smaller limit. Continue requesting a brief read-aloud answer in the built-in prompt.
- **API endpoint:** a separate non-secret world setting, initially `https://api.openai.com/v1/responses`. Use a complete HTTPS URL compatible with the Responses API. Show the destination in AI Connection. Changing it clears the session key, so a GM must enter a key for the new destination. Reject embedded URL credentials, query parameters, fragments, and automatic redirects.

Store the trimmed API key in a private module variable bound to the current world and GM user. Clear the input after use. Never put the key in `game.settings`, localStorage, sessionStorage, IndexedDB, Actor/User/ChatMessage flags, sockets, logs, macros, or module files. Do not expose a public getter for it. Reloading, closing the tab, logging out, changing user/world, or losing the GM role clears access. **Clear key** releases the key and cancels queued/in-flight AI work for that session; cancellation cannot guarantee that an already-submitted request incurs no API charge.

Each GM tab has its own session. The active GM who handles question requests must enter the key in that tab; other GMs' keys are never transferred. Once entered, the key is reused automatically for subsequent questions in that session.

New questions use the built-in answer instructions from `scripts/recall-knowledge-prompt.js`, with no configurable prompt setting. Retain that exact text with each saved prompt for later API attempts. Existing questions and retries keep their original instructions, including prompts created before the setting was removed.

This keeps credentials out of saved world data and players' clients, but does not make the GM browser a secret vault. Other code or extensions running there could capture the input or outgoing authorization header. OpenAI recommends server-side key storage; this design deliberately uses session-only browser storage to accommodate Forge without an external service. [OpenAI authentication guidance](https://developers.openai.com/api/reference/overview)

### Question and answer flow

1. Preserve the existing player dialog, owned source token, single target, question, and applicable Lore selection. Send only the question, token identities, Lore choice, requester ID, and operation ID through the existing authenticated GM transport.
2. The active GM validates the requester and tokens, makes the secret roll, applies the existing skill/DC rules, and freezes the compacted creature reference and LLM prompt. Preserve the ordinary best-skill comparison and the chosen Lore's DC reduction of 5 for a trait match or 3 otherwise.
3. Create the existing blind, GM-whispered question card and save its operation marker, original roll, prompt, and factual type/traits. Acknowledge the player's request once that card exists. Close the player's dialog and return to play; do not await OpenAI inside the player-to-GM request-response path.
4. If the active GM has a key, queue the saved question for an async API request. The private card shows **"Queued…"**, then **"Thinking…"**. Process one AI request at a time in that GM tab; waiting for the network does not block Foundry controls or other module actions.
5. When a valid answer arrives, post a separate GM-whispered answer message, with `blind: false` and no rolls. Its content and flags contain only read-aloud text, factual type/traits, and opaque question/operation/attempt IDs needed to avoid duplicate delivery; never copy the prompt, creature reference, DC, degree, skill, or request fingerprint onto it. Retain the original mechanical card's recipients and blind status. Save the answer message ID on that card and show **"Answer posted separately."**. The GM can review and make only the answer public. Do not automatically share it with players.
6. If the key is missing, show only the question card's non-API content and existing **Copy** prompt action; omit AI statuses and connection/get-answer/retry controls. Key entry remains in game settings. Entering a key restores card controls without silently submitting a backlog; the active GM chooses **Get answer** on the desired card.

### API request and answer handling

Use browser `fetch` with async/await to POST to the configured endpoint, defaulting to `https://api.openai.com/v1/responses`. Use the session key only in the HTTPS `Authorization: Bearer …` header; omit browser cookies and reject redirects. Bind each session key to the endpoint shown when it was entered. This uses the OpenAI API rather than automating the ChatGPT website; API billing is separate from a ChatGPT subscription.

Send the existing saved prompt as `input`, with trusted answer instructions in `instructions`. Treat the user's question and creature descriptions as reference material, not executable instructions. Capture the model, reasoning effort, and output allowance when reserving each attempt. Send the selected `model`, `reasoning: { effort }` for reasoning-capable models, and `max_output_tokens` using the output allowance (initially 4,000). Set `store: false`, and leave tools, streaming, background mode, and conversation history disabled for the first implementation. If the output allowance is reached, show a GM-only error suggesting an increase and manual retry. Async network I/O is sufficient for a responsive UI. Use a separate 90-second API timeout via AbortController, independent of the existing 60-second GM acknowledgment timeout. [Responses API](https://developers.openai.com/api/reference/python/resources/responses/methods/create)

`store: false` avoids requesting saved response history for later API retrieval; it does not promise that OpenAI keeps no logs or temporarily retained data. The question and compacted creature reference are sent to OpenAI. [Response storage](https://developers.openai.com/api/docs/guides/migrate-to-responses), [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)

For raw REST responses, collect text from the assistant's `output` message items and their `output_text` content parts. Do not assume the SDK-only aggregate `output_text` helper exists on the raw JSON response. Treat refusals, empty text, incomplete output, and malformed responses as explicit failures rather than completed answers.

Log one `console.warn` per actual API attempt with whitelisted numeric usage fields and an estimated USD credit cost, using documented model rates dated 2026-10-12. Support `gpt-6-luna` and `gpt-4.1-mini`/`gpt-4.1-mini-2025-04-14`, accounting for cache reads/writes, the returned processing tier, and GPT-6 Luna's long-context premium. Reasoning tokens are already included in output tokens and must not be charged twice. Report unknown cost instead of zero when usage or pricing is unavailable, including HTTP/network failures. Log returned usage before answer validation so incomplete or refused responses can still report their usage. Do not log credentials, prompt/answer text, arbitrary model/tier strings, endpoint URLs, or raw provider bodies, and do not persist the cost in chat. A chat-delivery-only retry must not create another usage warning. Cost estimates are not authoritative account-balance deductions.

Preserve the current prompt's degree-specific behavior: accurate focused information on success, truthful identification with no useful extra information on failure, a believable false recollection on critical failure, and an accurate answer plus a useful related fact on critical success. Always display the creature's type and all traits from the saved GM reference, independently of the model's wording. The answer should be flavorful and ready to read aloud, without revealing the roll, DC, degree, or GM notes.

Request plain text prose without Markdown or HTML formatting. Strip leftover presentation markup before saving and posting the answer. Put the shareable text in a separate answer-only ChatMessage marker and restore its literal text after Foundry enrichment for both GM and player views, even after the GM changes visibility to public. Do not run generated HTML, scripts, inline rolls, UUID links, or other Foundry actions embedded in model text. Keep the answer message free of Copy buttons and leave the original question card's prompt **Copy** action and clipboard fallback intact.

### Failures, retries, and interrupted sessions

Extend the private question marker with AI status, handling GM ID, attempt ID, model, timestamps, response ID, and answer or a sanitized error. Never include credentials. Reserve an attempt before any await so duplicate clicks and replayed player submissions join the existing job instead of starting additional paid requests. Keep the original question operation ID and roll across all AI retries.

Translate authentication, unavailable model, quota/rate-limit, network, browser connection-policy, and timeout errors into concise GM-only messages. Leave the saved prompt available and offer **Retry** or **AI Connection** as appropriate. Do not automatically retry paid API requests: after an uncertain network failure, OpenAI may already have processed the first attempt. A manual retry may incur another charge, but must never reroll Recall Knowledge.

For HTTP 429 responses, recognize `error.code` values for depleted prepaid credits, organization/project spending limits, organization usage limits, insufficient quota, rate limiting, and slow-down requests. Fall back to recognized `error.type` values or a generic HTTP 429 message for other providers. Use only locally authored guidance; do not persist or log raw provider messages or unknown codes/types. For temporary throttling, show a positive numeric `Retry-After` delay when supplied. Reading the error body remains asynchronous and covered by the API timeout.

If OpenAI succeeds but creating the answer message or updating the original card fails, retain the answer in memory and retry chat delivery without calling OpenAI again. Reuse an answer already posted for that question/operation/attempt, including after a lost acknowledgment, reload, or GM handoff; never change a reused answer's public/private visibility. Accept a late result only if the same GM session and attempt still own the job, the user remains a GM, the private card still exists, and no newer attempt has replaced it. Abort on an active-GM change and prevent the old handler from overwriting a new attempt.

After a reload or GM handoff, retained question cards and completed answers remain in chat, but the key and in-memory queue are gone. Mark abandoned pending attempts **"Interrupted"** when the new active GM initializes. Re-enter the key and explicitly retry any desired question using its saved prompt and roll; do not automatically resend pending requests. All API-related card controls execute only on the active GM, validate the private message/operation, and reject player attempts to invoke them through sockets or the public API.
