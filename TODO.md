## Review of v0.1.22 — 2026-09-25

Reviewed the builder, runtime, GM worker and socket transport, shared helpers, supplied macros and effects, examples, tests, and release packaging. All 75 existing automated tests passed. Additional isolated checks reproduced several cases that those tests do not cover; this review did not run a live Foundry world. **High** means a risk of losing saved work or applying/removing the wrong game result. **Medium** identifies narrower correctness or reliability problems. Items marked **Improvement** are preventive changes. Existing item numbers and resolved history remain unchanged.

16. ~~**Resolved: Dismissing an old zone preserves its saved preset revision.** GM and player creation now store the preset revision used by the zone. Dismiss restores that original revision, so Save rejects an overwrite if the preset changed later. Zones made before revision tracking retain an unknown revision and cannot silently overwrite the current preset; Save As remains available. Regression tests cover both creation paths and a stale save.~~

17. **High — Bug: Continuous effects can bypass or suppress a required saving throw.** The builder permits a block to combine “While a creature is inside,” Entry, and a saving throw. Continuous processing always applies the No Save result and marks the block's repeat limit; Entry then finds that limit already used and never requests its save. With the default Once each round setting, this combination was reproduced without any save request. Reject unsupported combinations with a clear explanation, or separate ongoing maintenance from save-triggered results and their repeat tracking. Code: [runtime.js](scripts/runtime.js#L1083), [zone-config.js](scripts/zone-config.js#L398).

18. ~~**Resolved: Lasting conditions keep their own source and removal rule.** Every zone-created Condition now has its own Item, including one set to Normal PF2e handling. PF2e still uses the strongest active value, while another zone's exit or dismissal removes only its own temporary Item. Normal Conditions remain after their zone ends and do not add cleanup records. Regression tests cover stronger and weaker overlapping values, independent lasting sources, and repeated application from one source.~~

19. **High — Bug: Failed cleanup can leave permanent effects while dismissal reports success.** `deleteOwnedItem` catches a failed deletion, but `deleteAppliedRecord` still discards its tracking record. A failed cleanup can therefore leave an unlimited Effect Item on an Actor with no retry record. Separately, `endZone` catches a failed Region deletion and returns normally, so Manage Zones and the GM worker report a successful dismissal even when the zone remains. Both failure paths were reproduced. Propagate meaningful failure results, retain cleanup records until removal succeeds, and make unfinished cleanup recoverable. Code: [runtime.js](scripts/runtime.js#L745), [runtime.js](scripts/runtime.js#L1256), [runtime.js](scripts/runtime.js#L1659).

20. **Medium — Bug: A save rolled while the GM is disconnected can lose its result.** If the live chat hook misses a save, `hasPending` later finds its valid result in chat and simply deletes the pending request. It does not apply the result's conditions, damage, or immunity. Startup also does not replay these completed saves. Reconcile pending requests against existing chat through the normal authorized resolution path, once per result. This complements item 11: that item handles unanswered saves; this one handles saves that were answered but never applied. Code: [runtime.js](scripts/runtime.js#L547), [runtime.js](scripts/runtime.js#L559), [runtime.js](scripts/runtime.js#L2391).

21. **Medium — Bug: Refreshing during activation can leave a zone permanently in its activation window.** The one-second activation timer is temporary, but `activationFinalizeScheduled` is saved on the Region. If the GM refreshes or authority changes after that flag is saved, the new runtime sees it and does not schedule a replacement timer. An isolated reload-state check left activation pending indefinitely. Original occupants can then continue being treated as initial occupants on later re-entry. Recover unfinished activation after startup, and keep timer ownership in runtime memory or use a persisted deadline that can be resumed. Code: [runtime.js](scripts/runtime.js#L1441).

22. **Medium — Bug: Combat on one Scene can expire zones on another.** The runtime scans zones across all Scenes but uses the GM client's single `game.combat` for their clocks. A Scene A zone can become attached to Scene B's encounter and expire when that unrelated encounter advances; this was reproduced without advancing world time. Resolve the appropriate encounter for each zone and source, and use world time when no matching encounter exists. The same scene-aware choice should be used for round-based repeat limits. Code: [zone-creation.js](scripts/zone-creation.js#L61), [runtime.js](scripts/runtime.js#L485), [runtime.js](scripts/runtime.js#L1527).

23. **Medium — Bug: Entering combat can restart temporary immunity's full duration.** When an immunity created outside combat is attached to an encounter, `syncImmunityCombatClock` keeps its original round count instead of its remaining time. A one-minute immunity with six seconds left was reproduced as still active several rounds into combat. Immunity also retains an old encounter ID after changing encounters. Preserve the remaining duration across these transitions, as the zone-duration code already attempts to do, so creatures become eligible again when expected. Code: [runtime.js](scripts/runtime.js#L313), [runtime.js](scripts/runtime.js#L343).

24. **Medium — Bug: Moving an area from another GM client can miss creatures along its path.** The old footprint is captured only in `preUpdateRegion`, and only on the authoritative GM. Foundry calls that hook only on the client initiating the update. If a second GM moves the area, the authoritative GM receives the final update without the old footprint, so the special swept-path Entry check cannot run; creatures outside the final position can be missed. Maintain a previous-shape snapshot on the authority or transfer the required movement data. Code: [runtime.js](scripts/runtime.js#L2257). Reference: [Foundry's preUpdateDocument hook](https://foundryvtt.com/api/functions/hookEvents.preUpdateDocument.html).

25. **Medium — Bug: Overlapping builder actions can create duplicates or overwrite edits made while saving.** Create disables its button only after asynchronous validation and damage-type selection. Two clicks during that wait were reproduced as two Region creations. Save and Save As also allow overlapping requests, and a delayed save response replaces the editor with its older configuration even if the user has continued editing. Reserve the action before the first wait, retain its source/preset snapshot, and ignore stale UI responses. Give retried creation requests a stable operation ID so a delayed GM reply does not encourage duplicate zones. Code: [builder.js](scripts/builder.js#L1311), [builder.js](scripts/builder.js#L1933), [transport.js](scripts/transport.js#L17).

26. **Medium — Bug: Concurrent Shielding Taunts can leave two targets taunted by one Guardian.** Each request collects the Guardian's existing Taunts before creating the replacement. Two requests that overlap during document creation can both see the same old state, apply their new effects, and leave both targets taunted. This was reproduced with asynchronous Item creation. Serialize this operation per Guardian and recheck the prior effects within that operation, so fast repeat clicks or overlapping player/GM requests still leave one current Taunt. Code: [shielding-taunt-worker.js](scripts/shielding-taunt-worker.js#L105).

27. **Medium — Bug: Effects copied from Actor sheets retain their previous source and aura cleanup metadata.** The module clones the whole Effect Item and replaces only its own zone flag. An Item previously applied by a native PF2e aura can retain `flags.pf2e.aura`, allowing PF2e to remove the new copy according to the old aura. Its `system.context.origin` can also still identify the previous caster; a compendium Item without origin instead falls back to its recipient in PF2e. Prepare a fresh zone application with the current source and target context and remove incompatible application-specific metadata while preserving its rules. Code: [runtime.js](scripts/runtime.js#L845). References: [PF2e aura cleanup](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/actor/helpers.ts), [PF2e effect origins](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/item/abstract-effect/document.ts).

28. **Medium — Bug: An expired Effect Item can block later applications.** When PF2e keeps expired effects on a sheet instead of deleting them, `addEffectItem` still finds the expired Item and treats it as an active duplicate. A creature can trigger the zone again, but receive no fresh effect. This was reproduced with an expired tracked Item. Check expiry and deliberately replace or refresh an expired application when the configured trigger permits another one. Code: [runtime.js](scripts/runtime.js#L850). Reference: [PF2e Effect Item expiry](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/item/effect/document.ts).

29. **Medium — Bug: Imported Effect Blocks can share an ID and interfere with each other.** Normalization preserves supplied block IDs without checking uniqueness; a duplicated ID passed the current validator in an isolated check. Repeat limits, pending saves, activation tracking, and outcome lookup use that ID, so copying a block in JSON can make one block suppress another or resolve a save using the wrong block's outcomes. Require unique, nonempty IDs or regenerate collisions during import, with a clear migration rule for existing configurations. Code: [zone-config.js](scripts/zone-config.js#L309), [runtime.js](scripts/runtime.js#L1725).

30. **Medium — Bug: Invalid imported choices can silently become different settings.** An unknown duration value becomes Unlimited, even under strict normalization, and unknown condition slugs pass validation. When an unrecognized condition is rendered in a dropdown with no matching option, the browser selects another available condition and the next form read saves that replacement. This is separate from item 9's fixed size/duration-input issue. Validate supplied enum values and condition slugs, retain unavailable selections visibly, and distinguish documented legacy migrations from typos. This prevents an imported configuration from changing behavior without the user realizing it. Code: [zone-config.js](scripts/zone-config.js#L237), [builder.js](scripts/builder.js#L375).

31. **Medium — Bug: Missing Actor statistics can appear as usable DC 0 choices.** `statisticDc` converts a missing value through `Number(null)`, producing zero. An Actor without a spell DC was reproduced with a selectable Highest Spell DC of 0 that passes configuration validation; the runtime later refuses to request the save. Preserve missing values as missing, list only positive DCs, and validate the resolved number before allowing creation. This gives the user an actionable field error instead of a zone that fails when triggered. Code: [dc.js](scripts/dc.js#L2), [zone-config.js](scripts/zone-config.js#L74), [runtime.js](scripts/runtime.js#L644).

32. **Medium — Bug: A failed Effect Item lookup stays cached for the entire builder session.** Resolving a UUID once stores its success or failure permanently in `effectLookupCache`. If a temporary lookup failure is corrected, or the Item is renamed or replaced, editing the same UUID reuses the stale result. A cached failure can keep Create disabled until the builder is reopened or the Item is dropped again. Invalidate affected cache entries on Item changes, allow an explicit retry, and refresh the cache from action-time validation. Code: [builder.js](scripts/builder.js#L1007).

33. **Medium — Bug: An unused, hidden outcome can block creation.** The new Effect Item resolver checks every outcome, including Failure/Success rows hidden when saving throws are disabled. An isolated check confirmed that a deleted Item in a hidden Failure row rejects a valid No Save configuration. Users cannot see the offending field without re-enabling saves. Validate only outcomes the block will actually execute, or show inactive-reference problems as clearly labeled warnings with a way to reveal them. Apply the same rule to live readiness and GM validation. Code: [effect-items.js](scripts/effect-items.js#L19), [builder.js](scripts/builder.js#L1050).

34. **Medium — Bug: A partly completed operation is reported as though nothing succeeded.** Preset saving writes the authoritative Journal flag before updating the readable index page. If the index update fails, the client sees a failed save even though its preset was stored; retrying a new Save can create another record. Creation similarly can store a Region and then fail during activation, leaving a zone behind while the UI reports failure. Return the committed result with a separate follow-up error, or make the remaining step safely resumable, so retries do not duplicate work and users know what exists. Code: [worker.js](scripts/worker.js#L193), [zone-creation.js](scripts/zone-creation.js#L158).

35. **Improvement: Limit retained runtime history and avoid unchanged writes.** Damage/healing roll caches, resolved-save records, and some applied-item references accumulate for the entire lifetime of a zone. Every state transaction writes the whole payload, and condition changes currently visit and rewrite all module zones even when most have no relevant watcher. For unlimited auras used across sessions, this increases stored data and network traffic. Prune records once no pending save needs them, remove stale Item references, and skip writes when nothing changed. This would improve responsiveness without changing the zone's rules. Code: [runtime.js](scripts/runtime.js#L174), [runtime.js](scripts/runtime.js#L931), [runtime.js](scripts/runtime.js#L1825).
